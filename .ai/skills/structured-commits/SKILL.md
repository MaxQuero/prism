# Commits structurés (gitmoji + Conventional Commits)

Skill projet Prism. Aligné sur l'historique existant (`✨ feat(ml-engine): …`).

## Format obligatoire

```
<gitmoji> <type>(<scope>): <sujet>
```

| Partie | Règle |
|--------|-------|
| **gitmoji** | Un seul emoji en tête (Unicode, pas `:shortcode:`) |
| **type** | `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `style`, `perf`, `ci`, `build` |
| **scope** | Zone impactée : `ml-engine`, `gateway`, `dashboard`, `infra`, `root` |
| **sujet** | Impératif, minuscules, sans point final, ≤ 72 caractères, en anglais |

Corps optionnel (ligne vide puis paragraphes) : expliquer le **pourquoi**, pas le quoi (le diff le montre). Footer optionnel : `Closes #123`, `BREAKING CHANGE: …`.

## Interdictions

- **Jamais** de signature ou mention d'origine : pas de `Generated by Cursor`, `Co-authored-by: Cursor`, `AI-generated`, `Written with …`, ni équivalent.
- Pas de sujet vague (`fix stuff`, `update`, `wip`).
- Pas de mélange de sujets non liés dans un même commit.
- Ne pas committer de secrets (`.env`, clés, tokens).

## Workflow

### 1. Analyser l'état

Exécuter en parallèle :

```bash
git status
git diff          # changements non stagés
git diff --cached # changements stagés
git log --oneline -10
```

### 2. Découper (atomicité)

Un commit = **une intention reviewable**. Séparer si les changements touchent des scopes, types ou sujets différents.

| Situation | Action |
|-----------|--------|
| feat + fix dans le même diff | 2 commits minimum |
| `ml-engine` + `gateway` | 1 commit par scope |
| refactor large + feature | refactor d'abord, feat ensuite |
| lockfile / config / code métier | commits séparés si reviewables séparément |
| notebook + code service | séparer sauf si indissociable |

Ordre recommandé : `chore`/`refactor` → `feat`/`fix` → `docs`/`test`.

### 3. Rédiger le message

1. Choisir type → gitmoji (voir [gitmoji-reference.md](gitmoji-reference.md)).
2. Identifier le scope principal (un seul ; le plus spécifique).
3. Rédiger le sujet : verbe à l'impératif (`add`, `fix`, `remove`, `align`).
4. Ajouter un corps seulement si le pourquoi n'est pas évident.
5. Référencer une issue GitLab dans le corps ou le footer : `#<numéro>`.

### 4. Stager et committer

- Stager **uniquement** les fichiers du commit courant (`git add <paths>`).
- Committer **uniquement si l'utilisateur l'a demandé explicitement**.
- Message via HEREDOC :

```bash
git commit -m "$(cat <<'EOF'
✨ feat(ml-engine): add forecast horizon mapping

Map RTE horizons to internal prediction windows for Chronos inference.

Closes #42
EOF
)"
```

- Si un hook pre-commit modifie des fichiers : les inclure dans un **nouveau** commit (pas d'amend sauf règle projet explicite).
- Ne pas push sauf demande explicite.

## Exemples (style Prism)

```
✨ feat(ml-engine): add realized consumption via RTE short-term API
🐛 fix(gateway): handle expired OAuth token refresh
🔧 chore(gateway): drop yarn lockfile in favor of npm
♻️ refactor(ml-engine): extract RTE client behind port interface
📝 docs(root): document local uv setup for ml-engine
✅ test(ml-engine): cover horizon mapping edge cases
🔧 chore(infra): align postgres layout and compose healthchecks
```

### Mauvais → bon

| ❌ | ✅ |
|----|-----|
| `update code` | `✨ feat(gateway): add JWT validation middleware` |
| `🐛 fix: bug` | `🐛 fix(ml-engine): handle empty RTE response body` |
| `feat: Added endpoint` | `✨ feat(ml-engine): add forecast consumption endpoint` |
| `✨ feat: stuff` | `✨ feat(ml-engine): add chronos zero-shot inference notebook` |
| Corps : « Generated by Cursor » | *(aucune mention d'outil)* |

## Checklist avant commit

- [ ] Un seul type / scope / intention par commit
- [ ] Gitmoji cohérent avec le type
- [ ] Sujet impératif, concis, en anglais
- [ ] Aucune mention Cursor / IA / génération automatique
- [ ] Pas de secrets dans le staging
- [ ] Issue GitLab référencée si applicable
